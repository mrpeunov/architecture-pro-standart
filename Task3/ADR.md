### **Функциональные требования**

| **№** | **Действующие лица или системы**           | **Use Case**                      | **Описание**                                                                                                                                          |
|:-----:|:-------------------------------------------|:----------------------------------|:------------------------------------------------------------------------------------------------------------------------------------------------------|
|   1   | Клиент                                     | Подача заявки через сайт          | Клиент заходит на страницу депозитов, выбирает из списка актуальных депозитов и заполняет форму (ФИО + Телефон)                                       |
|   2   | Клиент                                     | Подача заявки через интернет-банк | Клиент заходит экран депозитов, выбирает из списка актуальных и персонализированных депозитов и заполняет форму (Сумма + подтверждение с помощью СМС) |
|   3   | Сотрудник колл-центра, система колл-центра | Обработка заявок                  | Менеджер колл-центра обрабатывает заявку, звонит клиенту и предлагает особые условия                                                                  |
|   4   | Сотрудник бэк-офиса, АБС                   | Подтверждение депозита            | Сотрудник бэк-офиса обрабатывает заявку и открывает депозит в АБС                                                                                     |
|   5   | АБС, СМС-Шлюз, Клиент                      | Отправка сообщений клиенту        | Клиент получает сообщение отправление АБС через СМС-Шлюз при изменении статуса заявки                                                                 |

### **Нефункциональные требования**

| **№** | **Требование**                                                                            |
|:-----:|:------------------------------------------------------------------------------------------|
|  U1   | Интерфейсы оформления заявок на кредит и депозит должны быть удобными.                    |
|  U2   | Интерфейс должен соответствовать корпоративной системе дизайна.                           |
|  R1   | SLA 99.9% 24/7.                                                                           |
|  R2   | Данные передаваемые из интернет-банка и сайта должны шифроваться.                         |

|  S2   | Необходимо использовать известные команде технологии                                      |

### **Решение**

Сделать новый сервис для работы с депозитами. В MVP он будет работать только с онлайн заявками на депозиты,
но в будущем он может заменить ту часть монолита АБС, которая отвечает за работу с депозитами и стать
основной системой для управления обслуживанием депозитных продуктов.

Описание работы сервиса:
- Сервис будет иметь внутреннюю статусную модель.
- При создании заявки через сайт или через интернет-банк будет создаваться заявка во внутренней базе.
- После создании заявки во внутренней базе будет создаваться тикет в системе колл-центра.
- После закрытия тикета заявка будет переходить в статус, в котором её будет брать в работу менеджер бек-офиса депозитного отделения.
- Менеджер будет обрабатывать заявку и вносить её в АБС, в дальнейшем это может быть автоматизировано.

Схемы:
- [Схема контекста](context.puml)
- [Схема контейнеров](container.puml)

Данное решение позволит учесть все требование и будет хорошим подспорьем для будущей цифровой трансформации банка. 

Технологически стек у системы будет совпадать с системой колл-центра:
 - Веб-интерфейс на React.js;
 - Бэкенд на Java Spring Boot;
 - База PostgreSQL.

Причины:
- В команде АБС есть несколько специалистов с опытом в Java-стеке;
- Стек современный;
- База PostgreSQL уже есть в контуре и является одним из лучших решений, чтобы в будущем мигрировать на неё всё из Oracle и MS SQL.


### **Альтернативы**
Альтернативно можно реализовать онлайн депозит в рамках АБС, 
но это может создать дополнительную нагрузку на уже перегруженную систему и 
продолжит тянуть компанию в монолитный мир, что затруднит развитие цифровых продуктов.

**Недостатки, ограничения, риски**

Возможно в данном стеке будет недостаточно специалистов и придётся переучивать часть команды или наниматься со стороны.
Так как решение по стеку не является ключевым для данной ADR, то возможно стоит опросить команду о направлениях, в которых они хотят развиваться.

Так как решение шаг в сторону микросервисной архитектуры, то в будущем могут потребоваться инвестиции в DevOps: создание k8s-кластера, настройка service mesh и т.д.
